SOLID: năm nguyên tắc thiết kế qua những ví dụ đời thường

2026-11-03 #solid #lập trình hướng đối tượng #kiến trúc phần mềm #embedded

SOLID là tên của năm nguyên tắc rất quan trọng khi lập trình, nhất là lập trình hướng đối tượng. Bài này đi từng chữ cái theo một cách: mỗi nguyên tắc bắt đầu bằng một hình ảnh đời thường, rồi quay lại đúng hình ảnh đó trong code.

SOLID là gì

SOLID là chữ cái đầu của năm nguyên tắc: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. Ngôn ngữ không có class vẫn dùng được; áp dụng năm nguyên tắc này thì chương trình dễ hiểu hơn, linh hoạt hơn, và dễ bảo trì, mở rộng hơn.

Cả năm thật ra cùng giải một bài toán: khi yêu cầu thay đổi, chỉ phải đổi ít chỗ nhất và không làm hỏng chỗ khác. Mô phỏng dưới đây cho thấy điều đó bằng hình ảnh đời thường. Chọn một nguyên tắc, chọn cách sai hoặc cách đúng, rồi gửi một yêu cầu thay đổi và xem chỗ nào phải sửa.

S · Single Responsibility: mỗi class một việc

Hình dung một cái vừa là nĩa vừa là muỗng. Nó làm được cả hai việc nhưng không việc nào tốt, và hễ muốn đổi phần muỗng thì phần nĩa bị vạ lây. Tách ra nĩa riêng, muỗng riêng: mỗi thứ có một nhiệm vụ, sửa thứ này không đụng thứ kia.

Nguyên tắc. Một class chỉ nên có một nhiệm vụ. Vì chỉ có một nhiệm vụ nên khi nó thay đổi, ảnh hưởng lên chương trình là ít nhất.

Bây giờ là class Item. Nó giữ dữ liệu của món hàng, nhưng cũng tự hiển thị giá cho khách, tự xuất JSON cho đối tác và tự ghi xuống DB. Ba việc, và ba nhóm người khác nhau có quyền đòi sửa nó. Chú ý hàm phụ normalize: cả ba việc cùng gọi nó.

class FakeDb {
  rows: string[] = [];
  insert(name: string, price: number): void {
    this.rows.push(`('${name}', ${price})`);
  }
}

// ===== Trước: ItemAll gánh ba việc =====
class ItemAll {
  name: string;
  price: number;
  constructor(name: string, price: number) {
    this.name = name;
    this.price = price;
  }

  // Hàm phụ dùng chung cho cả ba việc bên dưới.
  protected normalize(n: number): number {
    return Math.round(n);
  }

  // Việc 1: hiển thị giá cho khách (nhóm sản phẩm quyết định)
  priceLabel(): string {
    return this.normalize(this.price) + " đ";
  }

  // Việc 2: JSON gửi đối tác (đối tác quyết định)
  toJson(): string {
    return JSON.stringify({ name: this.name, price: this.normalize(this.price) });
  }

  // Việc 3: lưu xuống DB (đội dữ liệu quyết định)
  saveToDb(db: FakeDb): void {
    db.insert(this.name, this.normalize(this.price));
  }
}

// Nhóm sản phẩm xin "giá hiển thị làm tròn đến nghìn đồng".
// Người sửa mở normalize ra đổi một dòng (viết thành lớp con để đặt cạnh bản cũ):
class ItemAllEdited extends ItemAll {
  protected normalize(n: number): number {
    return Math.round(n / 1000) * 1000;
  }
}

Cách tách: Item chỉ còn giữ dữ liệu, ba việc kia chuyển cho ba class riêng. Cùng yêu cầu ấy, lần này người sửa chỉ chạm vào PriceLabel.

// ===== Sau: mỗi class một việc =====
class Item {
  readonly name: string;
  readonly price: number;
  constructor(name: string, price: number) {
    this.name = name;
    this.price = price;
  }
}

// Việc 1: hiển thị giá cho khách
class PriceLabel {
  format(item: Item): string {
    return item.price + " đ";
  }
}

// Việc 2: JSON gửi đối tác
class ItemJson {
  encode(item: Item): string {
    return JSON.stringify({ name: item.name, price: item.price });
  }
}

// Việc 3: lưu xuống DB
class ItemRepository {
  private db: FakeDb;
  constructor(db: FakeDb) {
    this.db = db;
  }
  save(item: Item): void {
    this.db.insert(item.name, item.price);
  }
}

// Cùng yêu cầu ấy, lần này chỉ PriceLabel bị sửa:
class PriceLabelEdited extends PriceLabel {
  format(item: Item): string {
    return Math.round(item.price / 1000) * 1000 + " đ";
  }
}

Ví dụ tính tay · vì sao 12345 thành 12000

  1. Giá món hàng là 12345. Yêu cầu mới làm normalize(n) trả về Math.round(n / 1000) * 1000.
  2. 12345 / 1000 = 12.345, làm tròn được 12, nhân lại 12 * 1000 = 12000.
  3. Bản gộp gọi normalize ở ba nơi (priceLabel, toJson, saveToDb), nên cả ba đều ra 12000. JSON đối tác và DB mất đúng 12345 - 12000 = 345 đồng; không ai cố ý, chỉ vì chung một hàm phụ.
  4. Bản tách chỉ PriceLabel làm tròn; ItemJson và ItemRepository vẫn đọc item.price là 12345.

Cắt cả dữ liệu: gom field cùng ý nghĩa

Tách việc là một nửa của nguyên tắc này. Nửa còn lại nằm ở phần dữ liệu: nếu một class có quá nhiều field thì chắc chắn trong đó có những nhóm field luôn đi cùng nhau. Ở đây price luôn đi với currency, còn width, height, weight luôn đi với nhau. Gom mỗi nhóm thành một class nhỏ rồi ghép lại vào Item (kỹ thuật này gọi là aggregation hoặc composition).

O · Open/Closed: thêm bằng cách lắp thêm, không mở máy ra sửa

Hình dung một cái máy trộn có ổ cắm phụ kiện: đánh trứng, xay, nhào bột. Muốn thêm chức năng ép trái cây thì mua thêm một phụ kiện cắm vào. Bạn không phải mở thân máy ra sửa, càng không phải mua cả cái máy mới.

Nguyên tắc. Class nên mở cho việc mở rộng (thêm tính năng thoải mái) và đóng với việc sửa đổi (không phải can thiệp vào code đang chạy tốt).

Item của chúng ta đang xuất ra ba định dạng bằng ba hàm toJson, toXml, toHtml. Mai kia cần thêm YAML thì sao? Cách 1 là thêm toYaml vào Item: mỗi định dạng mới là một lần mở class đang chạy ra. Cách 2 dùng đa hình: tạo interface ItemEncoder có một hàm encode, mỗi định dạng là một class cài đặt nó. Item chỉ còn một hàm encode(encoder), và chỉ việc trả về encoder.encode(this).

// ===== Cách 1: mỗi định dạng là một hàm nằm trong Item =====
class ItemA {
  name: string;
  price: number;
  constructor(name: string, price: number) {
    this.name = name;
    this.price = price;
  }
  toJson(): string {
    return JSON.stringify({ name: this.name, price: this.price });
  }
  toXml(): string {
    return `<item name="${this.name}" price="${this.price}"/>`;
  }
  toHtml(): string {
    return `<li>${this.name}: ${this.price}</li>`;
  }
  // [mới] thêm YAML: phải mở class đang chạy ra thêm hàm
  toYaml(): string {
    return `name: ${this.name}\nprice: ${this.price}`;
  }
  // [hết mới]
}
// ===== Cách 2: Item chỉ biết "một encoder bất kỳ" =====
interface ItemEncoder {
  encode(item: Item): string;
}

class Item {
  name: string;
  price: number;
  constructor(name: string, price: number) {
    this.name = name;
    this.price = price;
  }
  encode(encoder: ItemEncoder): string {
    return encoder.encode(this);
  }
}

class JsonEncoder implements ItemEncoder {
  encode(item: Item): string {
    return JSON.stringify({ name: item.name, price: item.price });
  }
}

// [mới] thêm YAML: chỉ thêm một class, không sửa dòng nào ở trên
class YamlEncoder implements ItemEncoder {
  encode(item: Item): string {
    return `name: ${item.name}\nprice: ${item.price}`;
  }
}

Ví dụ tính tay · thêm YAML tốn bao nhiêu

  1. Cách 1. Thêm hàm toYaml dài 3 dòng vào trong ItemA. Class ItemA đã chạy ổn với ba định dạng giờ bị mở ra, nên phải kiểm lại cả bốn hàm: 3 + 1 = 4 test.
  2. Cách 2. Thêm class YamlEncoder dài 5 dòng ở chỗ khác. Item và ba encoder cũ không bị chạm vào dòng nào, nên chỉ cần 1 test mới cho YamlEncoder.
  3. Cách 2 viết nhiều dòng hơn (5 so với 3), nhưng không dòng nào nằm trong code đang chạy. Thêm định dạng thứ 5, thứ 6: cách 1 mở ItemA thêm hai lần nữa, cách 2 vẫn không mở lần nào.

Còn những hàm như saveToDb hay remove trong Item thì sao? Chúng cũng nên chuyển sang một interface khác để xử lý; phần I và phần D bên dưới nói đúng chuyện đó.

L · Liskov Substitution: con thay được cha mà chương trình vẫn đúng

Đây là nguyên tắc khó nhất trong năm cái. Lớp con kế thừa lớp cha, và lớp cha có những “lời hứa” về hành vi của mình. Lớp con được thêm hành vi mới, nhưng không được làm sai lời hứa đó.

Nguyên tắc. Chỗ nào đang dùng lớp cha, đem lớp con thay vào thì chương trình vẫn phải đúng. Lớp con không được thay đổi tính đúng đắn của chương trình.

Ví dụ 1: vận động viên

Lớp Sportsman (người chơi thể thao) hứa rằng người chơi thể thao thì khỏe. Một cử tạ Weightlifter kế thừa từ nó thì không sao, vì cử tạ còn khỏe hơn. Nhưng nếu một nhân vật ốm yếu cũng kế thừa Sportsman thì mọi đoạn code tin vào lời hứa “khỏe” đều sai. Lỗi này rất hay gặp trong chương trình hướng đối tượng.

// ===== Ví dụ 1: vận động viên =====
// Hợp đồng của lớp cha: người chơi thể thao thì khỏe (strength >= 7).
class Sportsman {
  strength(): number {
    return 8;
  }
}

class Weightlifter extends Sportsman {
  strength(): number {
    return 10;
  }
}

class Frail extends Sportsman {      // ốm yếu mà lại "là một" Sportsman
  strength(): number {
    return 2;
  }
}

function keepsPromise(s: Sportsman): boolean {
  return s.strength() >= 7;          // kiểm tra lời hứa của lớp cha, không quan tâm đây là lớp con nào
}

Ví dụ 2: mèo Tom và dòng super

Tom là nhân vật hoạt hình: bên ngoài là mèo nhưng cách cư xử như con người. Con mèo thật khi đi dùng bốn chân, và các chân cùng chuyển động. Coi con mèo là một hệ thống gồm nhiều module nhỏ (hai chân trước, hai chân sau, đuôi, đầu): gọi move() thì nó gọi xuống các module chân, cả bốn cùng bước. Đó là hành vi bắt buộc của lớp cha.

Tom đi hai chân. Nếu Tom ghi đè move() mà bỏ qua phần bắt buộc của lớp cha thì nó đã đổi hành vi vốn có của một con mèo. Cách đúng: gọi super.move() trước để làm phần việc của lớp cha, rồi mới thêm phần riêng của Tom. Đừng quên dòng super.

// ===== Ví dụ 2: con mèo và Tom =====
class Leg {
  steps = 0;
  step(): void {
    this.steps++;
  }
}

class Cat {
  // trước-trái, trước-phải, sau-trái, sau-phải
  legs: Leg[] = [new Leg(), new Leg(), new Leg(), new Leg()];

  // Hành vi bắt buộc của mọi con mèo: mỗi lần move(), cả bốn chân cùng bước.
  move(): void {
    for (const leg of this.legs) leg.step();
  }
}

// Sai: ghi đè move() mà bỏ luôn phần việc bắt buộc của lớp cha.
class TomBad extends Cat {
  move(): void {
    this.legs[2].step();
    this.legs[3].step();
  }
}

// Đúng: làm phần của lớp cha trước, rồi mới thêm phần riêng.
class Tom extends Cat {
  standing = false;
  move(): void {
    super.move();
    this.standing = true;
  }
}

// Đoạn code chỉ biết Cat: đi `n` bước rồi đếm số bước của từng chân.
function walk(animal: Cat, n: number): number[] {
  for (let i = 0; i < n; i++) animal.move();
  return animal.legs.map((leg) => leg.steps);
}
Truyền vào hàm walk(animal, n), vốn chỉ biết Cat
Dấu chân mỗi chân: – Tổng: – (kỳ vọng –)

Thử: chọn TomBad: hai chân trước đứng yên, tổng dấu chân chỉ bằng một nửa kỳ vọng. Chọn Tom: đủ bốn chân, và Tom vẫn có thêm hành vi riêng (standing = true).

Ví dụ tính tay · n = 3 bước

  1. Mèo thật: mỗi bước cả 4 chân cùng bước, sau 3 bước mỗi chân có 3 dấu: 4 × 3 = 12 dấu chân.
  2. TomBad chỉ bước hai chân sau: [0, 0, 3, 3], tổng 6. Đoạn code viết cho Cat kỳ vọng 12 nên tính sai.
  3. Tom gọi super.move() trước: [3, 3, 3, 3], tổng 12, đúng như mèo.

Ví dụ 3: hình chữ nhật và hình vuông

Ví dụ kinh điển nhất. Rectangle có chiều rộng, chiều cao, hàm setWidth, setHeight, và diện tích là rộng nhân cao. Hàm myApp nhận một Rectangle, đặt rộng 5, cao 10 rồi tính diện tích: ra 50, hoàn toàn đúng.

Sau đó chương trình mở rộng, có thêm hình vuông. Bạn cho Square kế thừa Rectangle vì hình vuông cũng là hình chữ nhật. Hình vuông thì rộng bằng cao, nên bạn “sửa” hai hàm set để gán cả hai cạnh. Cách làm đó chính là can thiệp vào hành vi của lớp cha.

// ===== Ví dụ 3: hình chữ nhật và hình vuông =====
interface Shape {
  area(): number;
}

class Rectangle implements Shape {
  protected w: number;
  protected h: number;
  constructor(w: number, h: number) {
    this.w = w;
    this.h = h;
  }
  setWidth(w: number): void {
    this.w = w;
  }
  setHeight(h: number): void {
    this.h = h;
  }
  area(): number {
    return this.w * this.h;
  }
}

// Sai: hình vuông kế thừa Rectangle rồi "sửa" các hàm set để hai cạnh luôn bằng nhau.
class BadSquare extends Rectangle {
  setWidth(w: number): void {
    this.w = w;
    this.h = w;
  }
  setHeight(h: number): void {
    this.w = h;
    this.h = h;
  }
}

// Đúng: Square và Rectangle cùng là Shape, không kế thừa nhau.
class Square implements Shape {
  side: number;
  constructor(side: number) {
    this.side = side;
  }
  area(): number {
    return this.side * this.side;
  }
}

I · Interface Segregation: đừng bắt ai gánh hàm họ không dùng

Hình dung một bảng điều khiển có năm nút gắn liền với nhau. Bạn chỉ cần hai nút mà vẫn phải nhận cả bảng, ba nút thừa vẫn phải bảo trì. Chia thành hai bảng nhỏ thì ai cần gì cầm cái đó, cần cả hai thì cầm cả hai.

Nguyên tắc. Thay vì một interface có rất nhiều hàm, hãy chia nó thành nhiều interface nhỏ. Nguyên tắc này khá giống Single Responsibility, chỉ khác là áp vào interface: tách interface to thành những đơn vị nhỏ hơn.

Ví dụ nhỏ trước: một interface EncoderDecoder chứa cả encode lẫn decode. Class nào cài đặt nó cũng bị ép viết cả hai hàm, dù chỉ cần một. Nên tách thành Encoder có hàm encode và Decoder có hàm decode; class nào cần cả hai thì cài cả hai.

// ===== Ví dụ nhỏ: mã hoá và giải mã =====
interface EncoderDecoder {
  encode(text: string): string;
  decode(text: string): string;
}

// Class chỉ cần mã hoá, nhưng interface bắt nó cài cả decode.
class EncodeOnlyFat implements EncoderDecoder {
  encode(text: string): string {
    return text.split("").reverse().join("");
  }
  decode(text: string): string {
    throw new Error("Không hỗ trợ");
  }
}

// Tách đôi: ai cần gì thì cài cái đó.
interface Encoder {
  encode(text: string): string;
}

interface Decoder {
  decode(text: string): string;
}

class ReverseEncoder implements Encoder {                 // chỉ mã hoá: chỉ 1 hàm
  encode(text: string): string {
    return text.split("").reverse().join("");
  }
}

class ReverseCodec implements Encoder, Decoder {          // cần cả hai thì cài cả hai
  encode(text: string): string {
    return text.split("").reverse().join("");
  }
  decode(text: string): string {
    return text.split("").reverse().join("");
  }
}

Tình huống thực tế hơn: một interface kho dữ liệu có năm hàm tạo, sửa, xóa, đọc một, đọc tất cả. Tách thành hai interface theo hướng dữ liệu: ItemWriter (dữ liệu đi vào: ba hàm) và ItemReader (dữ liệu đi ra: hai hàm). Bên nào cần cả năm hàm thì khai báo ItemStore kế thừa cả hai, không phải viết lại năm hàm.

// ===== Cách sai: một interface 5 hàm =====
interface ItemStoreFat {
  create(item: Item): void;
  update(item: Item): void;
  remove(id: number): void;
  findById(id: number): Item | undefined;
  findAll(): Item[];
}

// Báo cáo chỉ đọc, nhưng bị ép cài cả 5 hàm.
class ReportFat implements ItemStoreFat {
  private items: Item[];
  constructor(items: Item[]) {
    this.items = items;
  }
  create(item: Item): void {
    throw new Error("Không hỗ trợ");
  }
  update(item: Item): void {
    throw new Error("Không hỗ trợ");
  }
  remove(id: number): void {
    throw new Error("Không hỗ trợ");
  }
  findById(id: number): Item | undefined {
    return this.items.find((i) => i.id === id);
  }
  findAll(): Item[] {
    return this.items;
  }
}

// ===== Cách đúng: tách theo hướng dữ liệu =====
interface ItemWriter {          // dữ liệu đi vào kho
  create(item: Item): void;
  update(item: Item): void;
  remove(id: number): void;
}

interface ItemReader {          // dữ liệu đi ra khỏi kho
  findById(id: number): Item | undefined;
  findAll(): Item[];
}

interface ItemStore extends ItemWriter, ItemReader {}   // cần cả hai thì ghép lại

class ReportStore implements ItemReader {               // chỉ 2 hàm
  private items: Item[];
  constructor(items: Item[]) {
    this.items = items;
  }
  findById(id: number): Item | undefined {
    return this.items.find((i) => i.id === id);
  }
  findAll(): Item[] {
    return this.items;
  }
}

D · Dependency Inversion: đảo chiều mũi tên phụ thuộc

Hình dung một cái đèn bàn có dây điện hàn chết vào máy phát. Muốn đổi sang nguồn khác phải cắt dây ra hàn lại, tức là sửa cả cái đèn. Nếu đèn và nguồn đều chỉ cần khớp với một ổ cắm chuẩn thì đổi nguồn chỉ là rút ra cắm vào, đèn không đổi.

Nguyên tắc. Hai ý. Một: module cấp cao không được phụ thuộc module cấp thấp; cả hai nên phụ thuộc vào abstraction (interface). Hai: abstraction không được phụ thuộc chi tiết; chi tiết mới phải phụ thuộc vào abstraction.

“Cấp cao” và “cấp thấp” ở đây là mức chi tiết. Business logic (luật nghiệp vụ) là thành phần trừu tượng nhất, độ chi tiết thấp nhất. Presenter hay database có độ chi tiết cao hơn, nên là cấp thấp. Để các tầng không dính chặt vào nhau, chúng nói chuyện qua interface. Câu hỏi quyết định là: interface ấy khai báo ở đâu?

Cách thường gặp: interface nằm cùng tầng với database. Nó sẽ dễ định nghĩa theo chi tiết của database: nếu là MongoDB thì các hàm có kiểu ObjectId của Mongo. Hậu quả có hai. Một, business phải biết chi tiết của Mongo, đổi DB là đổi cả business. Hai, phải viết tầng data trước rồi mới viết được business, vì business phụ thuộc vào nó. Cách đảo ngược: interface nằm trong tầng business và dùng ngôn ngữ nghiệp vụ (priceOf(itemId)); tầng data phải cài đúng interface ấy. Mũi tên phụ thuộc giờ chỉ từ chi tiết lên nghiệp vụ.

// ===== Cách thường gặp: interface nằm ở tầng dữ liệu và mang hình dáng của MongoDB =====
class ObjectId {                                 // tầng DATA: kiểu id riêng của MongoDB
  hex: string;
  constructor(hex: string) {
    this.hex = hex;
  }
}

interface MongoItemApi {                         // tầng DATA
  findByObjectId(id: ObjectId): number | undefined;
}

class OrderServiceA {                            // tầng BUSINESS
  private store: MongoItemApi;
  constructor(store: MongoItemApi) {
    this.store = store;
  }
  total(hexIds: string[]): number {
    let sum = 0;
    for (const hex of hexIds) sum += this.store.findByObjectId(new ObjectId(hex)) ?? 0;
    return sum;
  }
}
// ===== Đảo ngược: interface nằm ở tầng nghiệp vụ và nói bằng ngôn ngữ nghiệp vụ =====
interface ItemStore {                            // tầng BUSINESS
  priceOf(itemId: string): number;
}

class OrderService {                             // tầng BUSINESS
  private store: ItemStore;
  constructor(store: ItemStore) {
    this.store = store;
  }
  total(itemIds: string[]): number {
    let sum = 0;
    for (const id of itemIds) sum += this.store.priceOf(id);
    return sum;
  }
}

class MongoItemStore implements ItemStore {      // tầng DATA: chi tiết cắm vào interface
  constructor() {
    throw new Error("Không kết nối được MongoDB: chưa có máy chủ");
  }
  priceOf(itemId: string): number {
    return 0;
  }
}

class MemoryItemStore implements ItemStore {     // tầng DATA: bản giả để test
  private prices: Record<string, number>;
  constructor(prices: Record<string, number>) {
    this.prices = prices;
  }
  priceOf(itemId: string): number {
    return this.prices[itemId] ?? 0;
  }
}

Nhìn lại Item sau khi áp dụng cả bốn nguyên tắc có thể làm trên cùng một ví dụ. Chữ cái bên cạnh mỗi khối cho biết nó đến từ nguyên tắc nào. Riêng chữ L không có khối riêng: nó là lời hứa chung cho mọi mũi tên đứt nét, rằng bản cài đặt nào cắm vào interface cũng phải giữ đúng hợp đồng.

Ôn lại bằng cách tự thử. Mỗi câu dưới đây là một tình huống ngắn: bạn chọn nó vi phạm nguyên tắc nào (hoặc không vi phạm nguyên tắc nào) và xem lời giải thích.

Đừng áp dụng quá tay. SOLID có chi phí trả trước: thêm class, thêm interface, thêm chỗ phải đọc. Chương trình nhỏ, một cài đặt duy nhất, không bao giờ đổi thì class gộp ngắn gọn hơn. Ba quy tắc thực dụng: (1) đã có hai bản cài đặt, hoặc cần bản giả để test thì tạo interface; (2) đã phải sửa cùng một chỗ lần thứ hai thì tách ở chỗ đó; (3) chưa có lý do thì giữ đơn giản, vì tách sau chỉ là di chuyển code.
